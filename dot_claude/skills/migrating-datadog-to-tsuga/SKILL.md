# Migrating Datadog monitors and dashboards to Tsuga

## Overview
The Tsuga auto-import keeps Datadog names, formulas (often wrong), message syntax and broken layouts. The goal is correct, readable, verified monitors and dashboards, not a 1:1 copy. Simplest result wins: merge, drop, and fix Datadog bugs instead of copying them.

Rules: [monitors.md](monitors.md), [dashboards.md](dashboards.md), Tsuga quirks: [tsuga-gotchas.md](tsuga-gotchas.md). Read the ones you need before editing. Tsuga docs (`search-docs`, `get-doc-page`) override this skill when they disagree.

**No assumptions**: state only what you verified with data, a tool call or a file. Anything else (tool behavior, what a handle routes to, whether a rule can filter on an attribute, a sample interval) is labeled unverified or asked to the user, never written as fact, in objects, Jira and the report. SLOs are out of scope: don't look for them, migrate them or report them.

## Workflow
1. **Inventory** both sides: Tsuga by name search (`searchQuery`) AND `service` tag (manual DD monitors often lack it); Datadog monitors and dashboards for the service, including ones created after the migration run. Read each DD monitor's `notifications` and message handles, then ask the user which of them page (don't infer it) and note which monitors use them and for which envs. Check whether the Tsuga objects are managed as code (search the IaC repos with the GitLab or sourcebot MCPs, or ask the user for the IaC path; an empty search proves nothing, so say which repos you searched): if so, change the code, not the API: you edit it, the user applies it, and `validated` is set in code once the applied object replays clean. The Jira ticket's list can be stale: query Tsuga yourself.
2. **Data first**: for every metric/log field, check Tsuga has data under the real name, per env (high `limit` on every groupBy level). Run every imported filter on its own too: DD tags (`landing-zone:gcp`, `kube_*`) often don't exist in Tsuga and a filter matching nothing makes a monitor that never evaluates. Empty = ingestion gap or renamed metric: fix or report it, don't polish an empty widget. Compare every DD threshold with the real per-env values (7d max/p95) (monitors.md, Query).
3. **Monitors**: apply monitors.md. Leave them `validated:review` until verified (step 5). Re-fetch the live monitor before every write: `update-monitor` replaces it, so a UI edit would be overwritten.
4. **Dashboards**: apply dashboards.md. Re-fetch the live dashboard before every write: the user edits in the UI.
5. **Verify**: replay each monitor query over 24h-7d with a bucket ≤ window/5. Run every dashboard widget query.
   A replay can't prove delivery. Unless a real alert and recovery of this monitor are already in the tests channel, propose the live test once (monitors.md; if declined, list it as unproven), then set `validated:true` if the monitor checks up (Ownership boundaries).
   Then, once the replacement is `validated:true`, delete the merged per-env Tsuga copies yourself: the user confirms each batch and you save the JSON first (durable directory, see Ownership boundaries). DD originals follow Ownership boundaries. A dropped monitor needs the user's confirmation and saved JSON, no replacement.
   Post-migration review of monitors already `true`: replay every monitor and run every widget query in parallel (one read-only subagent per service or dashboard group), report the findings, and change only what the user picks (re-fetch before writing). A monitor you changed and certified stays `true`.
   Before reporting, check with data, not memory: every "equivalent to Datadog" claim against Datadog values, how often each monitor fires in the replay, what the new dashboard doesn't cover. Anything unproven (does `@team-sre` page, sample interval) is a question to the user, not a fact. State what the API can't prove (rendering, units, recovery notifications).
6. **Report**: lead with every monitor left in `review` (its alert goes to the tests channel) and why, and every `oncall:true` monitor whose paging isn't routed (blocks deleting its DD original). Then what changed (every threshold change as old/new/why), what was dropped (with ids) and why, anything firing now. Jira (gotchas: Jira row): one short comment (about 5 lines: what exists, what was retuned vs DD, what was removed, what is unproven), edited in place with `commentId`, plus the description rewritten to the final objects. Then offer a short "beyond the rules" plan (coverage gaps, never-firing monitors, overlap, dashboard trims), ranked. Plan only until the user picks.
7. **Close**: when every monitor is `validated:true` (dashboards carry no `validated` tag) and the DD monitors are gone (verify with a Datadog search), propose ticking the description task list and closing the ticket; do it only if the user says so (SRE project: chain transitions `5` → `6` → `7` → `8`, never `2` "Aborted").

## Ownership boundaries
- `validated`: you set `true` once the monitor checks up (replay clean, data under every filter, message and tags correct, routing rules present, nothing unproven that matters; a declined live test, a recovery notification not seen after the clone's single edit, or an unreplayable healthy-by-design metric doesn't block it when the logic stands up and the replay succeeds); otherwise it stays `review`, with what blocks it in the report. Never demote a `true` monitor to `review` for rework or testing (live tests use a clone).
- DD originals stay active until the Tsuga replacement is `validated:true`; deleting them is a separate step: ask first, and not while an `oncall:true` replacement has no active paging rule. DD dashboards are never deleted; only monitors go. Never write "removed" before verifying.
- Crossplane-managed DD monitors (`managed-by:crossplane`) are removed by a change in the values repo (a local clone: ask the user for its path, sourcebot is read-only): drop the app's `generic-kube.monitors` block and the then-unused `generic-kube` dependency in each env `Chart.yaml` (`dependencies: []`), diff `helm template` before and after (other generic-kube features must not change). This step needs the user's go-ahead. `git status` first (the user may have edited already); never commit or push, suggest a title. Manual DD monitors: the user deletes them in the UI (Datadog tools are read-only).
- A live test creates a temporary monitor clone and may mutate a cluster (never edit the real monitor): state the exact changes (including the clone's single recovery edit), get an explicit yes, change nothing beyond it (if it goes wrong, restore, delete the clone and report). The yes covers that plan only: a new clone, a changed design or an extra edit needs a fresh yes.
- Never create or activate a paging notification rule. If the routing rules monitors.md expects are missing, or no paging rule is active, tell the user (tag `oncall:true` anyway).
- Merging per-env copies is the default (report it). Dropping a monitor with no replacement: explain why, then ask; save its JSON before any drop, in a durable directory under `$HOME` (the scratchpad can vanish mid-session).
